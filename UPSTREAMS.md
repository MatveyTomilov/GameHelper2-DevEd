# Upstream Sync

Мониторинг опрашивает все источники из `dev/upstream/sources.json` одним Linux-job каждые 30 минут. `branch: null` выбирает текущую основную ветку каждого репозитория. Проверяются SHA, ветка по умолчанию, теги, опубликованные релизы и сведения GitHub о лицензии. Compare API даёт файлы и сообщения для классификации. При неполном сравнении Issue получает `needs-analysis`.

`upstream/state` хранит исходные адреса, наблюдаемый и отдельно интегрированный SHA, теги, релизы и время последнего записанного контрольного состояния. При первом успешном чтении создаётся исходное состояние без Issue. Следующие Git-коммиты состояния возникают при обнаруженном изменении или при ручном обновлении интегрированного SHA. Последние успешные отметки каждого опроса хранятся в маленьком артефакте `upstream-checks` на 7 дней. Если артефакт недоступен, используются отметки контрольного состояния. GitHub Compare API ограничивает список файлов, поэтому при больших или разошедшихся изменениях требуется локальное сравнение.

Issue идентифицируется хешем перехода и ищется среди открытых и закрытых Issues. При ошибке чтения, записи Issue или state старое состояние источника остаётся доступным. Код из upstream не запускается. Workflow использует встроенный токен GitHub с `issues: write`, `contents: write` и `actions: read` только для собственного репозитория. Состояние публикуется в отдельной ветке. Изменения проекта проходят обычное ревью.

В `Actions → Upstream monitor → Run workflow` доступны `monitor` для реальной проверки, `fixture` для автономных тестов и `test-api` для контролируемой проверки API. Последний режим создаёт ровно один явно помеченный тестовый Issue, проверяет дедупликацию и закрывает его.

## Выборочный перенос

1. Возьмите старый и новый SHA из Issue. Запустите `./dev/upstream/compare.ps1 -Repository Gordin/GameHelper2 -Before <старый SHA> -After <новый SHA>`. Сценарий сохраняет объекты Git в локальном `artifacts/compare` и выводит коммиты и файлы.
2. Сверьте затронутые файлы с локальной интеграционной копией и проверьте происхождение и лицензию. Если права на размещение не подтверждены, держите изменения в локальной интеграции.
3. Создайте `upstream/<источник>-<короткий SHA>` от `develop`. Перенесите только проверенные изменения. Укажите URL, оригинальный SHA, автора и путь. Сохраните применимые copyright notices.
4. Соберите локальный Release и пройдите регрессионные проверки. Для офсетов отдельно используйте `recover.ps1` и сравните живые значения. Обновите `integrated` в конфигурации только после принятия конкретного изменения.
5. Откройте PR в `develop` с результатами тестов, описанием изменений и способом отката. Ручная интеграция в `main` выполняется после проверки новой сборки.

## Расход GitHub Actions

GitHub Free сейчас включает **$12 в месяц** на вычисления аккаунта. Стандартный `ubuntu-slim` стоит **$0.002 за тарифицируемую минуту**. GitHub округляет время каждого job вверх. При одной минуте за запуск 30-дневный месяц потребует **1 440 минут ($2.88)**, 31-дневный — **1 488 минут ($2.98)**. При двух минутах за запуск в 31-дневном месяце расчёт составляет **2 976 минут ($5.95)**. Ручные запуски прибавляются отдельно, а лимит разделяется с другими репозиториями владельца. У job таймаут 2 минуты, у скрипта 40 секунд, параллельные запуски блокирует одна группа concurrency. [Лимиты GitHub Free](https://docs.github.com/en/billing/reference/product-usage-included) · [Тарифы и округление](https://docs.github.com/en/billing/reference/actions-runner-pricing)

Для запрета платного превышения владелец открывает [Settings → Billing and licensing → Budgets and alerts](https://github.com/settings/billing/budgets), выбирает **New budget → Product-level budget → Actions**, область личного аккаунта или `GameHelper2-DevEd`, вводит **$0**, включает **Stop usage when budget limit is reached**, если поле доступно, и сохраняет. GitHub указывает, что пользовательский бюджет сам по себе имеет жёсткий предел. При отсутствии действующего способа оплаты GitHub блокирует исполнение сверх включённого объёма. Доступность поля и сохранённую сумму нужно проверить в настройках владельца. [Инструкция GitHub](https://docs.github.com/en/billing/how-tos/set-up-budgets)
